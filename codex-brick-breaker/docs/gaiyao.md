# 《打砖块》概要设计

## 1. 设计范围

本文档基于《[游戏设计文档](game-design.md)》描述首版浏览器单人打砖块游戏的整体技术方案。首版仅实现桌面浏览器、键盘操作、3 个关卡及既定的砖块、道具和结算规则。

## 2. 技术栈

| 类别 | 选型 | 用途与原因 |
| --- | --- | --- |
| 页面结构 | HTML5 | 承载游戏画布、信息栏、开始/暂停/结算界面和无障碍文本。 |
| 画面渲染 | Canvas 2D API | 高频绘制小球、砖块、挡板和粒子，避免大量 DOM 元素逐帧更新。 |
| 逻辑与交互 | 原生 JavaScript（ES Modules） | 实现游戏循环、碰撞、状态管理、键盘输入和 UI 更新；无需构建工具即可运行。 |
| 样式 | CSS3 | 布局 HUD、弹层、按钮、颜色主题和响应式画布容器。 |
| 持久化（可选） | `localStorage` | 保存最高分、静音偏好和已解锁关卡，不依赖后端。 |
| 音频（可选） | Web Audio API 或 `<audio>` | 播放短促碰撞及结算音效，并支持静音。 |

首版不引入游戏引擎、后端服务或第三方依赖，以减小项目体积和理解成本。

## 3. 总体架构

游戏采用“数据驱动的单页面 Canvas 应用”结构。HTML 负责静态容器与可交互界面；JavaScript 将运行数据更新后交给 Canvas 绘制；CSS 只控制非游戏画面部分的外观。

```text
HTML / CSS
  ├─ HUD：关卡、分数、生命、暂停
  ├─ 弹层：开始、暂停、通关、失败
  └─ Canvas：游戏画面

JavaScript
  ├─ Game：状态机、主循环、关卡切换
  ├─ Input：键盘状态
  ├─ Entities：挡板、小球、砖块、掉落道具
  ├─ Collision：边界与对象碰撞
  ├─ Level：关卡配置与实例化
  ├─ Renderer：Canvas 绘制
  └─ UI / Audio / Storage：外围能力
```

## 4. 模块划分

| 模块 | 核心职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| `Game` | 维护游戏状态、调度更新顺序、处理输赢与换关 | 输入事件、对象状态 | 当前帧游戏状态 |
| `Input` | 监听按键并维护左右移动、发球、暂停状态 | 浏览器键盘事件 | 标准化输入状态 |
| `Level` | 保存关卡砖块布局、速度倍率和生成规则 | 关卡编号 | 砖块实例及关卡参数 |
| `Paddle` | 计算挡板移动、边界限制、道具效果 | 输入、时间步长 | 挡板位置与尺寸 |
| `Ball` | 更新位置、速度、发球和失球状态 | 时间步长、碰撞结果 | 小球位置与速度 |
| `Brick` | 保存类型、耐久、分数和可破坏状态 | 命中事件 | 消失/受损/掉落事件 |
| `PowerUp` | 下落、接取、计时效果和失效 | 时间步长、挡板位置 | 对游戏状态的增益 |
| `Collision` | 判定对象相交并计算反弹方向 | 实体几何数据 | 碰撞事件与法线 |
| `Renderer` | 根据当前状态绘制一帧画面 | 游戏状态 | Canvas 图像 |
| `UI` | 更新文字、显示弹层、绑定按钮 | 游戏状态变化 | DOM 变化 |

## 5. 运行机制

### 5.1 主循环

使用 `requestAnimationFrame` 驱动渲染。每帧计算距上一帧的时间差 `deltaTime`，将其限制在合理上限后更新游戏状态，再绘制当前画面。

```text
requestAnimationFrame
  → 计算 deltaTime
  → 若状态为 PLAYING：更新输入、挡板、小球、道具与碰撞
  → 处理失球/清关/游戏结束
  → 更新 HUD 与弹层状态
  → 绘制 Canvas
  → 请求下一帧
```

`deltaTime` 以秒为单位参与速度计算，使游戏在不同刷新率显示器上保持近似一致的运动速度。页面失焦后恢复时，应限制单帧最大时间差，避免物体瞬移穿透。

### 5.2 状态机

| 状态 | 含义 | 可转换到 |
| --- | --- | --- |
| `START` | 首次进入，等待开始 | `READY` |
| `READY` | 小球附着在挡板上，等待发球 | `PLAYING`、`PAUSED` |
| `PLAYING` | 正在更新物理和计时 | `READY`、`LEVEL_CLEAR`、`GAME_OVER`、`PAUSED` |
| `PAUSED` | 暂停所有游戏时间 | `READY`、`PLAYING` |
| `LEVEL_CLEAR` | 当前关卡完成，显示结算 | `READY`、`VICTORY` |
| `GAME_OVER` | 生命耗尽 | `START` |
| `VICTORY` | 最终通关 | `START` |

## 6. 关键实现方案

### 6.1 坐标与尺寸

采用 Canvas 内部像素坐标：左上角为 `(0, 0)`，x 轴向右，y 轴向下。逻辑尺寸固定，例如 `800 × 600`；CSS 根据容器缩放显示，鼠标/触摸扩展时再按缩放比换算坐标。

### 6.2 碰撞策略

- 墙壁与挡板：小球使用圆形边界，按越界方向翻转对应速度分量。
- 砖块：使用“圆形小球与矩形砖块”的最近点判定。计算小球圆心到矩形最近点的距离，小于球半径即为命中。
- 反弹面：比较小球进入砖块前后的边界或最小穿透方向，选择水平或垂直法线反转速度；命中砖块后将小球推出砖块边缘，防止连续重复命中。
- 运动稳定性：每帧位移过大时可将更新拆分为多个小步，降低高速小球穿过薄砖块的概率。

### 6.3 挡板反弹角度

以挡板中心为参考，计算命中点的标准化偏移 `offset`（范围约为 `-1` 到 `1`），并映射到最大反弹角（建议 60°）。最终速度方向由角度生成，y 分量强制向上，同时保留当前速度大小并保证最小垂直分量。

### 6.4 关卡数据化

每个关卡使用二维数组或砖块配置列表描述。格子值映射到砖块类型，关卡加载时依据统一的边距、行列间隔和砖块尺寸生成实体。这样新增关卡只需增加数据，而无需修改游戏循环。

### 6.5 临时效果

扩展、减速和穿透均使用“效果名 → 到期时间/参数”的结构维护。每帧检查到期时间并恢复基础值；重新获取同类道具时刷新时长而非无限叠加。多球不使用全局计时，在新增小球离场后自然结束。

## 7. 数据流

```text
键盘事件 → Input 状态
              ↓
requestAnimationFrame → Game.update(deltaTime)
  → Paddle / Ball / PowerUp 更新
  → Collision 生成命中事件
  → Brick、得分、生命、效果、状态机更新
              ↓
        Renderer 绘制 Canvas + UI 更新 HUD / 弹层
```

## 9. 性能与兼容性

- 首版实体数量很少，直接逐个检测小球与砖块即可，不需要空间索引。
- `requestAnimationFrame` 会在后台标签页自动降频，适合浏览器小游戏。
- Canvas 绘制应以清屏后重绘整帧为主，减少复杂的局部擦除逻辑。
- 目标浏览器为现代 Chrome、Edge、Firefox 和 Safari 的近年版本。
- 无法播放音频不应阻塞游戏；`localStorage` 不可用时可忽略保存功能。

## 10. 测试重点

- 不同帧率下的移动速度与小球反弹是否稳定。
- 球命中砖块边角、连续命中以及高速移动时是否正确。
- 最后一个多球离场时是否只扣除一次生命。
- 暂停后道具倒计时、球和掉落物是否冻结。
- 关卡切换、重新开始后是否清理旧小球、道具和效果。
